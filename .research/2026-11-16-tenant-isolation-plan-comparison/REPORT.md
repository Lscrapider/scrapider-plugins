# 同一真实副本上的三份租户隔离计划

本轮使用业务副本中真实存在的批次、上传和流水线代码。目标是比较执行计划的派发、验收和执行可读性。三份计划都有可开始的代码工作。第二档的任务存在循环前置，第三档的协作结构最清楚且需要修正方案，Superpowers 抓到了一个两份 Scrapider 原稿漏掉的数据库约束。三份原稿均保留。

## 会影响实际执行的发现

1. **分片会话键是共同漏项。** 旧实现 ChunkUploadServiceImpl.java:150 用文件 MD5 取会话，:225 把 MD5 写入会话 file_id，:241 插入。scripts/java-sqls/schema/003-file-chunk-upload.sql:22 的唯一索引只看 file_id。两份 Scrapider 原稿只改查询范围，按原稿的新行为，B 不会复用 A 的会话，又不能用相同 MD5 插入自己的会话。Superpowers Task 3 把该持久键一起纳入。这一点比文档格式优劣更影响实际交付。复核的正例要让 A、B 用相同 MD5 得到各自会话，并保留旧对象的全局引用保护。
2. **第二档存在可具体指出的循环。** 对照总计划第 30–34 行与实施步骤第 74、85、106 行，按文档严格派发，做完 T02 后 D2 依赖 T03，T03 又依赖 D2。用具体结果替换阶段名。T03 取 T02 已可用的有租户批次父查询和认证契约，T04 取 T02 的批次归属查询，T06 将可提前准备的迁移脚本与启用区分开。在[静态复演](targeted-replay.txt)中，修改这些输入后可走到最后一步，仅真实 fixture 缺失影响切换验证。
3. **第三档的分工最明确，首个技术方案仍需收口。** B00 第 19–20 行及 B03 第 16、26 行计划新增内部 Maven 模块依赖。旧 auth 和 dashboard 的 pom 均无 business-common 直接边，共同题面禁止加依赖。D1 可借用既有认证主体携带可信租户并让 HTTP 入口传标量，或者使用已有可见层的共享契约，适配当前已存在的 POM 图。B01 中 Controller 要传 userId，但接口文件和其他调用方要与实现一起分配。齐全后按原 D5 组合验收。
4. **Superpowers 对本地步骤更直接，也有无法单独落地的签名变更。** Task 2 第 62 行改变 createBatch 等签名；原有 DataSyncServiceImpl.java:194 使用 createBatch(createParam, userId)。ArchiveUploadTaskExecutor.java:236 和 SyncExecutor.java:209 仍调用旧 verifyUpload。Task 3 虽有 ZIP 执行器，实际双向调用迁移无完整同组安排，同步路径也没写入负责文件。Task 7 的构建可以发现编译冲突，无法补齐前面被宣称逐项完成的输出。

## 这轮学到什么

- **协调者视角**采用第三档的共有交付记录与按边界的 Brief。启用条件单放，完成一份贡献可以先回传。接手上传的人从 B01 能找到同步和对象副作用路径。第二档无需在多个文档切换，适合一名主要执行者，前提是任务输入写具体。Superpowers 的任务顺序、接口位置和构建命令在此样本最易顺读。
- **验收**三路都描述了 A/B、混合绑定和异步重复；它们在真正上线前仍需非生产 fixture。已实际运行的是旧代码 45 例离线回归。相同 MD5 只观察「无跨租户命中」会错过本租户第二次正常上传能否成功。拒绝数据测试单独使用匹配的异租户 ID。
- **Skill 修订**将归属范围变化连到真实分配键、查找、唯一性和并发约束，要求用可在开工前存在的具体产物表示依赖，并在做方案时核对调用方已有模块依赖。用[小型静态调度及内存唯一约束复演](targeted-replay.txt)验证两条修订对应的结果。保留原稿以免事后修改对照分数。本轮为一个场景的一次写作对照。
